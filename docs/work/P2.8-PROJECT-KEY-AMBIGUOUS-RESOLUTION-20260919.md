## The defect

The `PROJECT_KEY_AMBIGUOUS` review is emitted when one `project_key` resolves to more
than one canonical project. Its `resolution_actions` advertised three operator
choices — `merge`, `canonical_key`, and `reject_match` — but **only `merge` actually
closed the review**. Root cause: the ambiguity was computed on each observation's
*raw* compatibility `project_key` hint (`facts[obs_id]["project_key"]`), not the
canonical project's *resolved* `project_key`. A `canonical_key` decision overrides the
resolved key only and never changes membership, so it could not affect a check keyed
on the raw hint; a `reject_match` also cannot reduce the hint-to-project cardinality to
1. The defect was a documentation/semantics inconsistency — the ambiguity was always
correctly surfaced, just not clearable by two of the three advertised actions.

## What changed

In `ledger/identity.py`, the `PROJECT_KEY_AMBIGUOUS` grouping now iterates the compiled
canonical `projects` and groups by each project's **resolved** `project_key` (the
`canonical_key` override already applied by the per-project auto-derive), instead of
iterating raw observation facts:

- A `canonical_key` decision that assigns a **distinct** key to one of two same-key
  projects now disambiguates the projects, so the ambiguity disappears and the review
  clears — matching the advertised `resolution_actions`.
- A genuine unresolved same-key collision (no disambiguating key) still opens the
  review with the **same** `review_id` as before (the affected observation set is
  unchanged), so the pinned r0 `the-garden` review ID
  (`rev_08eb96a0b8b7722ac70b2a20`) and the estate-3/4 review IDs are preserved.
- The raw `project_key` hint remains reachable as a `project_key_hint` referent on
  every project (unchanged behavior); the review `evidence` now references the
  resolved key (`{"kind": "project_key", ...}`).
- `resolution_actions` corrected to the two paths that actually clear: `merge` and
  `canonical_key`. `reason_automation_stopped` now states that a `reject_match` alone
  does **not** clear the warning because the human key remains shared across the
  distinct projects. (This is the Option B fold-in: the actions no longer advertise a
  resolution that the compiler does not accept.)

`canonical_key` and `reject_match` merge/split authority are unchanged: keys remain
referents, never automatic identity authority (SCHEMA.md invariant #2); `canonical_key`
still never changes project membership.
